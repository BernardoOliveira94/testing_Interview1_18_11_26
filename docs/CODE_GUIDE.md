# Code guide - what each file does, how to explain it, and how to retest fast

Everything is commented inside the files (JS files and the scripts inside the Postman YAML). This guide is the map.
JSON and YAML files cannot hold comments reliably, so their structure is explained here instead.

---------------------------------------------------------------------------------------------------------
## 1. File map: what to say about each one

| File | What it is | One-sentence explanation |
|---|---|---|
| `tests/api/google-books.spec.js` | Exercise 3 in Playwright (JavaScript) | "Each test sends one HTTP request and checks status code, JSON structure and the API rules." |
| `postman/` (YAML files) | Exercise 3 in Postman | "The same tests, but as a Postman collection with scripts in the Tests area." |
| `tests/portal/portal.spec.js` | Exercise 2 (portal) in Playwright | "Smoke tests of the public pages; login tests are prepared but disabled until there is a test account." |
| `playwright.config.js` | Playwright settings | "Defines two projects (API and portal), the base URLs, the reports and what is recorded on failure." |
| `tests/support/mock-books-server.js` + `run-with-mock.js` | Local fake Google Books API | "A simulation to prove the test logic works even when the real API is over quota. It does not replace the real run." |
| `app-appium/` | Exercise 1 (app) skeleton | "Appium + WebdriverIO, because Playwright cannot drive native apps. Not executed: needs a device and a test account." |
| `manual-tests/*.xlsx` | Exercises 1 and 2 (manual) | "Test cases by risk: money and security first, then negative, boundary and resilience cases." |
| `package.json` | Project description for Node | "Lists the dependency (Playwright) and the shortcut commands (`npm run test:api` ...)." |
| `package-lock.json` | Exact versions installed | "Generated automatically, guarantees the same versions on every computer. Never edit by hand." |
| `.env` (not in Git) | Your secrets | "API key and portal URL live here so they never go to GitHub." |
| `.env.example` | Template of `.env` | "Shows which values must be filled in, without the secrets." |
| `.gitignore` | Files Git must ignore | "Keeps secrets and generated folders (reports, node_modules) out of the repository." |
| `playwright-report/`, `test-results/` | Generated by every run | "Reports and traces. Safe to delete; they are recreated." |

### How to read `package.json` (JSON cannot have comments)
```json
{
  "scripts": {
    "test:api": "playwright test --project=google-books-api",   <- npm run test:api  = run only the API tests
    "test:api:mock": "node tests/support/run-with-mock.js",     <- same tests against the local fake API
    "test:portal": "playwright test --project=portal",          <- only the portal tests
    "test": "playwright test",                                  <- everything
    "report": "playwright show-report"                          <- open the last HTML report
  },
  "devDependencies": { "@playwright/test": "1.63.0" }           <- the library needed only for testing
}
```

### How to read a Postman request file (YAML)
```yaml
$kind: http-request            # this file is one request
description: ...               # text shown in Postman under the request name
url: "{{baseUrl}}/volumes?q=ios&maxResults=20&startIndex=0&key={{apiKey}}"   # {{...}} = variables
method: GET
headers: { Accept: application/json }   # we ask for JSON
queryParams: { q: ios, ... }            # the same parameters, in table form
scripts:
  - type: afterResponse        # JavaScript that runs AFTER the answer arrives = the "Tests" tab in Postman
    code: |-                   #   (the commented script is here)
order: 1000                    # position in the folder = run order
```
Variables: `{{baseUrl}}` and `{{apiKey}}` come from the **environment** ("Google Books - Env"). `volumeId` and `page1Ids`
are **collection variables** that the scripts fill in while running (that is how GB-01 passes an id to GB-08).

## 2. Mini glossary (for the words in the code)

| Word | Meaning |
|---|---|
| `require(...)` | Import a library. |
| `const` | A variable that is not reassigned. |
| `async` / `await` | "This takes time (network): wait for the answer before the next line." Every Playwright call needs `await`. |
| `{ request }` or `{ page }` in a test | Playwright "fixtures": ready-made tools given to the test (`request` = HTTP client, `page` = browser tab). |
| `expect(x).toBe(y)` | Assertion: the test fails if x is not y. |
| `expect.soft(...)` | Assertion that records a failure but lets the test continue. |
| `test.describe(...)` | Groups tests under one title. |
| `test.skip` / `test.fixme` | Do not run (skip = condition not met; fixme = known to need fixing/enabling). |
| `=> { }` | Arrow function (a short way to write a function). |
| `` `text ${x}` `` | Template string: inserts a value into text. |
| `...obj` | "Spread": copy the content of an object or list. |
| `.map()` / `.filter()` / `.some()` | Transform a list / keep matching items / "is at least one a match?". |
| `process.env.NAME` | A value read from the environment / `.env` file. |
| `pm.test`, `pm.expect`, `pm.response` | Postman's objects: define a check, make an assertion, read the answer. |
| Status 200 / 400 / 404 / 429 | OK / bad request / not found / too many requests (quota exceeded). |

## 3. Retest fast - Playwright (UI mode)

**Open UI mode:** in the VS Code terminal (project folder) run
```
npx playwright test --ui
```
What you see:
1. **Left panel:** all tests in a tree. The checkboxes at the top filter by project (`google-books-api`, `portal`).
2. **Run everything:** the play button at the top. **Run one test:** the small play icon that appears next to its name.
3. **Re-run quickly after changing code:** click the eye icon ("watch") next to a test or folder; it re-runs every time you save the file.
4. **After a run:** click a test to see its steps in the **Actions** list and the **Errors** tab for the failure message with "Expected / Received".
   Use the **Source** tab to see the line that failed.
5. **Stop or clear:** the stop button and the "clear results" (trash) icon in the toolbar.

**VS Code alternative:** install the extension "Playwright Test for VS Code", open the Testing icon (beaker) in the left bar,
and click the green play next to a test (right-click for "Debug test").

**Terminal shortcuts (fast retests):**
```
npm run test:api                                   # all API tests against the real API (needs the key in .env)
npm run test:api:mock                              # same tests against the local simulation
npx playwright test -g "GB-05"                     # only tests whose title contains GB-05
npx playwright test --project=google-books-api --last-failed   # only what failed in the previous run
npx playwright test --project=portal --headed      # watch the browser while the portal tests run
npx playwright test --debug                        # step through a test, line by line
npm run report                                     # open the HTML report of the last run
```

**If everything fails with "429":** the API key is missing or invalid, or the Books API is not enabled for the key's project.
Check `.env` (key without quotes or spaces) and run again.

## 4. Retest fast - Postman (desktop app)

1. **Open the collection** "Google Books API - Automated Tests" in the left sidebar. (It is loaded from the `postman/` folder of the repository.)
2. **Choose the environment** in the top-right dropdown: "Google Books - Env". Open it (eye icon) and make sure `apiKey` has YOUR key.
   `baseUrl` must be `https://www.googleapis.com/books/v1`.
3. **Run one request:** click it (for example GB-05) and press **Send**. In the answer panel open the **Test Results** tab:
   green = pass, red = fail with the reason. The **Body** tab shows the JSON answer.
4. **Run the whole collection:** right-click the collection (or the "..." menu) > **Run collection** > leave the order as is > **Run**.
   The result lists every request and every check. Use **Run again** to repeat.
5. **Order matters:** GB-01 saves `volumeId` (used by GB-08) and GB-03a saves the page-1 ids (used by GB-03b).
   If GB-08 fails with an empty id, run GB-01 first.
6. **Look at the variables:** open the collection > **Variables** tab to see `volumeId` and `page1Ids` change after a run.
7. **Debug:** open the **Postman Console** (bottom-left "Console") to see every request and response that was sent.
8. **After editing a script:** save (Ctrl+S) and Send again.

Command-line alternative (optional): `npx newman run <collection> -e <environment> --env-var "apiKey=YOUR_KEY"`.
(Newman reads the Postman JSON export; export the collection from Postman first.)

## 5. Things that will probably be asked, with short answers

| Question | Short answer |
|---|---|
| Why Playwright for an API? | It has a built-in HTTP client, it is fast, and I can keep API and UI tests in one project. |
| Why also Postman? | Quick to explore and share an API; collections can run in a runner or from the command line. |
| What does a good API test check? | Status code, response structure/schema, business rules, error format, and performance. Not exact data that changes. |
| Why check the 429 explicitly? | A quota error would otherwise look like a valid 4xx in negative tests and make them pass for the wrong reason. |
| What did you find with the real API? | The pagination test failed on the first real run: the API can repeat one item between neighbouring pages. I changed the assertion to what the API really guarantees and documented why. |
| Why a mock server? | To prove the test logic runs independently of the real API. It is a simulation, not a replacement. |
| Why is the app only a skeleton? | It needs a device, a test build and test accounts; banking apps often block emulators and need SMS/biometrics. |
| Why are the login tests `fixme`? | They need a test account and the real locators; I did not want to invent them. |
| How do you avoid flaky tests? | Stable locators, built-in waiting (no fixed sleeps), independent tests, no dependence on exact content. |

## 6. Security rules for the repository
- Never commit `.env` or any file that contains the API key. The Postman environment file is ignored in `.gitignore` for that reason.
- If a key was ever committed or shared, delete it in Google Cloud Console (APIs & Services > Credentials) and create a new one. Removing it from a later commit is not enough, because Git history keeps it.
- Restrict the new key to the Books API.
